# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Teamer è un tool di gestione team multi-utente: più **director** (ognuno vede solo i suoi team, vedi «Perimetri»; nessuno è sopra gli altri), un profilo **HR** trasversale (vede tutti, scrive contratti e RAL, gestisce la configurazione aziendale) e un **site admin** IT che gestisce utenti, audit, backup e aggiornamenti senza vedere dati del personale. Funzioni: organigramma, retribuzione (RAL, benefit, budget aumenti/assunzioni, montepremi, listino), valutazioni 9-box, ciclo annuale obiettivi/review/benessere, note 1:1, simulazioni di riorganizzazione, report. UI, commenti e commit in italiano. Non c'è un linter configurato.

## Comandi

```bash
make setup      # uv sync (su mac sqlcipher3 compila contro brew sqlcipher; se fallisce:
                #   CFLAGS="-I$(brew --prefix sqlcipher)/include" LDFLAGS="-L$(brew --prefix sqlcipher)/lib" make setup)
make dev        # uvicorn --reload su http://127.0.0.1:8000
make seed       # DB demo in data/teamer.db (utenti coo/admin, password demo12345678) — rifiuta se il DB esiste già
make key        # chiave di sistema di sviluppo in data/dev.key (la creano già dev e seed)
make test       # pytest
uv run pytest tests/test_services.py -q                  # un file
uv run pytest tests/test_db.py::test_wrong_key -q        # un singolo test
```

### Rilascio e aggiornamenti

Ogni incremento finito (feature o fix) si chiude con bump `version` in `pyproject.toml` → `uv lock` → commit → **tag annotato** → push (anche del tag). La **GitHub Release** si fa solo quando una versione è compiuta (un blocco di lavoro coerente, verificato anche e2e), non a ogni tag: gli incrementi intermedi sono tag patch (`0.47.1`, `0.47.2`…), la release chiude la serie (`0.48.0`) con le note di tutto il blocco. L'updater legge `releases/latest` sul canale **stabile** (produzione): un tag senza Release non ci arriva, ed è voluto. Sul canale **anteprima** (`data/update/channel` = `tag`, scelto dall'admin in Aggiornamenti; `teamer-update --channel tag`) prende il tag più alto anche senza Release: è per l'istanza di test. Mai downgrade. Le istanze si aggiornano **dall'app** (Amministrazione → Aggiornamenti, solo il site admin: l'app scrive `data/update/request`, la path unit `teamer-update.path` lancia `teamer-update` come root; vedi `app/services/updater.py` e `deploy/install/`) oppure con `pct exec <ctid> -- /usr/local/bin/teamer-update`. I dettagli della macchina di sviluppo e dei container (host, chiavi, firma) stanno in `CLAUDE.local.md`, non versionato.

`teamer-update` non tocca mai `/opt/teamer/data` (DB), `.env` né la chiave `/etc/teamer/db.key`: prima dello swap copia il DB in `data/backups/` (ultimi 5), se `uv sync` fallisce fa rollback, e a fine corsa installa unit systemd, `teamer-admin` e sé stesso dalla release nuova. L'installer genera la chiave e il primo site admin (`teamer-admin init`). Un'istanza ≤ 0.29 passa alla 0.30 con la procedura del README («Passaggio dalla versione mono-utente»): due `teamer-update`, `teamer-admin init`, migrazione dal browser con la vecchia password, `teamer-admin create-admin`. Attenzione per le release future: il primo `teamer-update` gira con l'updater **vecchio**, quindi un file nuovo da installare (binario o unit) arriva solo alla passata successiva. L'installer da zero è `deploy/ct/teamer.sh` (standalone stile community-scripts: il loro `build.func` non supporta install-script di repo terzi); il repo è pubblico, il token serve solo a un fork privato. Un container su **due reti** (`BRIDGE2`…, 0.37.1) risponde a ognuna dal suo gateway con `deploy/install/teamer-multihome` (rotte per sorgente, hook dhclient o `post-up`): il gateway della seconda rete non va mai in `gw=` del container.

## Architettura

**Stack**: FastAPI + Jinja2 + htmx (niente SPA, niente build step), SQLite cifrato con SQLCipher, Python gestito da `uv`. Tutti gli asset (htmx, Chart.js, font DM Sans/Serif) sono vendored in `app/static/`: l'app deve funzionare offline, mai aggiungere risorse da CDN.

**Database — il cuore delle convenzioni** (`app/db.py`, `migrations/`):
- **Connessioni** (`app/db.py`): una **di sistema** (`db.sys.*`, usata anche dagli helper quando non c'è una sessione di director: login, admin, CLI, test) e **una per ogni sessione di director**, aperta al primo uso e chiusa al blocco/uscita (`session.on_close`). Ogni connessione ha il suo lock; file in WAL, `BEGIN IMMEDIATE` in `transaction()`, ordine dei lock `_gate` → sessione → sistema. Le scritture passano da `db.qualify()` che le manda a `main.<t>`: nel codice dell'app le tabelle si scrivono per nome letterale, mai con schema, mai `executescript` (`tests/test_sql_scritture.py` lo verifica sull'AST, con gli `ON CONFLICT` che devono combaciare con una UNIQUE). Utenti, audit e pannello admin usano `db.sys`. È la base dei perimetri per director: sulla connessione di sessione `perimeter.install()` crea guardie e viste temporanee.
- **Perimetri per director** (`app/perimeter.py`) — tutti i director sono uguali, l'app non presume gerarchie fra loro né una figura di vertice:
  - **Classi**: ogni tabella sta in una classe di `perimeter.CLASSES` (`owned`, `child`, `team`, `person`, `authored`, `company`, `instance`); `tests/test_perimeter.py` fallisce finché una tabella nuova non è classificata. `authored` (0.37) = note 1:1 e azioni, con `author_user_id DEFAULT (teamer_owner())`: ognuno vede e scrive solo le proprie, a prescindere dal perimetro della persona; se la persona passa a un altro director restano all'autore in sola lettura (l'azione si può ancora chiudere) e il nome arriva dalla vista temporanea `perim_note_person`.
  - **Proprietario**: configurazione del director, cicli, budget, montepremi, simulazioni (e figli) e team hanno `owner_user_id INTEGER DEFAULT (teamer_owner()) REFERENCES app_user(id)`: la riga nuova prende il proprietario dalla funzione registrata sulla connessione della sessione, senza toccare le INSERT. Si dichiara così nel `CREATE TABLE` (l'`ALTER` non accetta il default con funzione: si ricostruisce la tabella), UNIQUE con il proprietario, `ON CONFLICT` coerenti. NULL = «da assegnare» (lo assegna l'admin, `perimeter.assign_unassigned`).
  - **Visibilità**: ogni director vede solo i suoi team (`team.owner_user_id`) e le persone la cui ultima assegnazione valida sta lì (o senza assegnazione e create da lui, `person.owner_user_id`); tutti i dati di persona seguono la persona. Sulla connessione di sessione `perimeter.install()` crea tabelle temporanee `perim_*`, guardie `BEFORE` (prima) e viste temporanee omonime (dopo); poi un **authorizer** nega le letture di `main.<tabella>` fuori dalle viste, `app_user`/`audit_event` e `ATTACH`/`PRAGMA`/`VACUUM`. Tutta la suite gira sotto l'authorizer: una query che lo viola fallisce nei test.
  - **Nessuna funzione verso altri perimetri**: sopra il team più alto del director `org_tree.expected_manager` dà `OUTSIDE` (riporto salvato mai sovrascritto né segnalato), i form conservano padre/responsabile nascosti, le liste contengono solo i suoi. Le guardie sono l'ultima difesa (`IntegrityError` «fuori perimetro» → 403). Una scrittura fallita negli helper fa rollback subito (la transazione implicita terrebbe il lock sul file).
  - **Titolarità**: i dati «da assegnare» li assegna l'admin (`perimeter.assign_unassigned`); una persona passa a un altro director per mano di HR (`perimeter.transfer_person`, 0.40, dalla pagina Persone: nuova assegnazione storicizzata nel team tecnico «Da collocare» del destinatario, `team.holding`, avviso in dashboard finché non la colloca; tutto lo storico segue la persona, a chi cede non resta nulla, nessuna quota si sposta; «Correggi» (0.47.4) rimedia a un director sbagliato, sempre: annulla l'assegnazione corrente e ne apre una nel «Da collocare» del director scelto con la stessa data d'inizio, senza storico; i team non si muovono mai, il trasferimento di team non esiste più); `perimeter.REV` sale e le connessioni di sessione ricaricano il perimetro alla richiesta dopo.
  - **Configurazione del director**: questionario 9-box, aggiustamenti ruolo × anzianità, peso premio per casella, moltiplicatori premio, soglie RAL (chiavi in `user_meta`, instradate da `db.get_meta/set_meta`); il listino è aziendale dalla 0.41. Un director nuovo riceve quella di default (`perimeter.ensure_config` da `factory_config()`: le migrazioni su un DB in memoria).
  - **Configurazione aziendale** (classe `company`): liste valori (`lookup`), catalogo benefit, CCNL predefinito (`app_meta`). La gestisce `app/routers/company.py` (`/azienda`, ruolo in `company.MANAGED_BY`: **HR** dalla 0.41, senza ripiego sull'admin, che non vede dati del personale; il listino, codici e parametri, è il suo quarto tab) scrivendo con `db.sys`; dalle sessioni di director e HR l'authorizer ne nega la scrittura (l'import aggiunge i livelli via `db.sys`). Ciò che è per ruolo/anzianità/rating si costruisce dalle liste aziendali con default neutro, mai da elenchi fissi nel codice.
- La connessione di sistema si apre **all'avvio del servizio** (`db.startup()` nel lifespan) con la **chiave di sistema** letta da `config.DB_KEY_FILE` (`TEAMER_DB_KEY_FILE`, in produzione `/etc/teamer/db.key`, raw key SQLCipher `x'…'`): la conosce solo l'IT, gli utenti mai. Stati in `db.state()`: `pronto`, `chiave_mancante` (pagina «esegui teamer-admin init»), `legacy` (DB ≤ 0.29 cifrato con la password dell'unico utente di allora: `/login/migrazione` lo ricifra con `PRAGMA rekey` e crea il primo director con la stessa password). Chi trova il DB non aperto riceve `db.DatabaseLocked`, gestita in `main` con redirect/`HX-Redirect`.
- **Utenti e ruoli** (`app/users.py`, `auth.allowed(role, path, method)` nel middleware): `app_user` con hash scrypt (min 12 caratteri, backoff dopo 5 errori, `must_change_password` → ogni pagina rimanda a `/account`); si correggono in place e si **disattivano, mai cancellati**; deve restare almeno un admin attivo. Ruoli con nomi specifici, mai un generico `user` (i ruoli futuri si aggiungono accanto). CLI per l'IT: `app/admin_cli.py`, wrapper `deploy/install/teamer-admin`.
  - **`admin`** (site admin): solo `/admin*`, `/account`, `/lock`; `/` → `/admin`, il resto 403. Non vede dati del personale, con un'unica eccezione: i nomi delle persone Director+ per collegarle agli utenti director. Esporta l'audit filtrato in CSV/Excel (`/admin/audit/export.*`, evento anch'esso). Sceglie il canale degli aggiornamenti.
  - **`director`**: tutto tranne `/admin*`. È **collegato alla persona** che lo rappresenta (`app_user.person_id`): IT la sceglie creando l'utente, o dopo da Gestisci, fra le persone attive con ruolo Director+ (`users.DIRECTOR_ROLE = "sr"`) non ancora collegate (`users.linkable_people`); una persona collegata non si sposta ad altro director né si cessa finché IT non la scollega; un cambio di ruolo scollega. Il director **legge** contratti, RAL, benefit e incentivi (`auth.CONTRACT_POST` gli nega le scritture) e non censisce persone: decide aumenti (piano), sostituzioni e organizzazione dei suoi team.
  - **`hr`**: connessione di sessione a viste senza filtro (`perimeter._install_hr`) e configurazione propria di default; vede le persone di **tutti** i director; niente report/simulazioni/riporti/configurazione del director; dashboard propria su `/` (`reports._dashboard_hr`). Scrive solo dentro `auth.HR_WRITE_OK` + `perimeter.HR_WRITABLE`: note e azioni proprie; **contratti, RAL, benefit, incentivi e cessazioni** (solo suoi); censimento e import da Excel delle persone con la scelta del director (`/people/import`); RAL dirette dall'analisi salary (variazioni CCNL, senza piano); spostamento di una persona a un altro director; configurazione aziendale (`/azienda`: liste, benefit, CCNL, listino, moltiplicatori del premio di ruolo); montepremi per ruolo. Scelto un director **«in veste di»** (`POST /hr/acting`, `session.acting`, `hrview.context`), assunzioni, budget, piano e analisi salary diventano i suoi, con i form: ciò che crea nasce intestato a lui (`owner_user_id = COALESCE(?, teamer_owner())` con `hrview.owner()`). Senza director scelto consulta, con director per riga, filtro Director multiplo e totali (`app/routers/hrview.py`). I pulsanti dei form POST compaiono a HR solo nei form con classe `hr-ok` (CSS `body.hr-readonly`, rete di sicurezza).
  - **Piano aumenti**: macchina a stati in `compensation.PLAN_TRANSITIONS`; il director cambia l'importo solo in bozza (una proposta inviata la riporta in bozza), HR lo valida sulle proposte in attesa senza blocco sul tetto; approva e applica chi dei due arriva prima.
  - **Cessazione**: la registra HR dalla scheda; il director la trova in dashboard («Cessazioni da decidere») e sceglie sostituire (posizione con `hiring_position.replaces_person_id`) o no (`replacement_decision`, append-only, annullabile). Ogni posizione nuova dichiara se è un +1 al team o una sostituzione.
- **Ripristino/import** (`db.restore`, pannello Sistema e `teamer-admin restore`): il file porta i **dati**, `app_user` e `audit_event` (`db.INSTANCE_TABLES`) restano quelli dell'istanza e ci vengono copiati sopra. Si apre con la chiave dell'istanza, con quella di un'altra (`source_key`) o con la password ≤ 0.29; verifica integrità, che sia Teamer e non più recente (`latest_migration`), ricifra, migra (`_migrate(conn)` lavora su qualunque connessione), salva il DB attuale in `data/backups/teamer-pre-ripristino-*` e scambia il file sotto il lock. Da shell il wrapper ferma il servizio: mai scambiare il file sotto una connessione aperta da un altro processo.
- **Origine delle richieste** (0.47.5, CSRF): `main.origin_guard`, il middleware più esterno, rifiuta con 403 ogni richiesta non-GET di un'altra origine, login e battito compresi: in HTTPS decide `Sec-Fetch-Site` (vale anche dietro un reverse proxy), in HTTP `Origin` confrontato con `Host`/`X-Forwarded-Host`; senza nessuno dei due passa (non è un browser). Si aggiunge al cookie `SameSite=Lax`: nei form niente token. Lo stesso middleware (0.47.7) mette su ogni risposta `main.SECURITY_HEADERS` (CSP con sole risorse dell'app, `frame-ancestors 'none'`, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: same-origin`) e, in HTTPS (diretto o `X-Forwarded-Proto`), `Secure` su ogni cookie. La CSP ammette script e stili inline perché i template ne sono pieni, ma niente `eval`: htmx non deve usare `hx-on`, `js:` né filtri `[…]` nei trigger.
- **Esclusioni dell'analisi di sicurezza**: `patched.md` (radice) elenca i reperti degli scanner statici già esaminati, con regola, percorsi, motivo e condizioni `valid_while`; il sistema di verifica lo legge. Chi cambia il codice che giustifica un'esclusione (f-string SQL, `origin_guard`, `_raw`, updater, reaper) la riconferma o la toglie nello stesso commit; un'esclusione nuova si aggiunge solo dopo aver verificato il punto.
- **Audit** (`audit_event`, append-only): `users.audit()` prende l'utente dalla sessione corrente; il middleware registra un evento `azione` per ogni richiesta non-GET (metodo, path, esito — **mai il corpo**, può contenere cifre), salvo le anteprime `*/simulate`. Gli eventi di login/blocco/gestione utenti li scrivono `auth`, `users`, `admin`. L'admin esporta il registro filtrato in CSV o Excel (`/admin/audit/export.{csv,xlsx}`, 0.45; l'export stesso è un evento).
- **Blocco per sessione, senza timeout di inattività**: il cookie firmato porta l'id della sessione, il registro sta in memoria in `app/session.py` (un riavvio blocca tutti). Ogni pagina manda un battito (`app/static/js/teamer-session.js` → `POST /heartbeat`); quando l'ultima pagina **di quella sessione** si chiude, il reaper la blocca — il DB resta aperto per gli altri utenti. `/heartbeat` e `/unlock` stanno **fuori** dal guard di `main` e rispondono sempre JSON: una pagina con una nota a metà non deve mai essere trascinata via da una richiesta di sfondo. A sessione bloccata compare un overlay che chiede utente e password e sblocca in place (il testo non salvato resta, e un submit trattenuto riparte da solo). «Esci» (`POST /lock`) chiude solo la propria sessione.
- Migrazioni = file SQL numerati in `migrations/`, applicati in ordine all'avvio (`schema_version` in `app_meta`). Ogni modifica di schema è un nuovo file, mai editare i vecchi.
- **Append-only**: ciò che evolve (RAL, assegnazioni, contratti, valutazioni) non si aggiorna, si aggiunge un record; lo stato corrente è `end_date IS NULL` / l'ultimo evento. Le tabelle a eventi hanno `created_at`, `voided`, `void_reason`: gli errori si annullano (`voided=1`), non si cancellano. Le query di stato filtrano sempre `voided=0`.
- Un contenitore (budget aumenti, budget assunzioni, montepremi) **senza movimenti** si elimina anche se chiuso (0.47, `deletable` nelle route di lista); con movimenti si chiude e resta nello storico. Regola UX correlata: ogni entità offre due strade distinte — il **cambiamento reale** (nuovo record storicizzato: "Nuova assegnazione", nuovo evento RAL) e la **correzione di un errore** (form "Correggi" in place, void, o delete guardato). Mantenerla per ogni feature nuova. Per i **documenti** (nota 1:1) il cambiamento reale è una nota nuova e la correzione è la modifica in place: non c'è stato derivato da storicizzare, quindi niente `voided`.
- Config in tabelle, non nel codice: pick-list in `lookup` (i dati salvano il `code`, le etichette si rinominano e si propagano), aggiustamenti 9-box in `ninebox_weight`, moltiplicatori del premio composito in `bonus_factor` (del director) e del premio di ruolo in `bonus_role_factor` (aziendale), codici di listino in `listino_profile` (aziendale), configurazione del director in `user_meta`, default aziendali (CCNL, parametri del listino) in `app_meta`.
- **Questionario 9-box** (per director, `evaluation_model.config`): domande con asse `perf`/`pot`, peso, nome breve, note per ruolo/anzianità, risposte con punteggio 1–3, più le 9 caselle; si modifica dall'editor in Configurazione → 9-box (mai JSON a mano). `ninebox_calc.normalize/validate/score`: ogni asse è la media pesata delle sue risposte. Il wizard manda gli **indici** delle risposte; ogni valutazione salva il questionario usato in `ninebox_assessment.model_snapshot` e il risultato lo rilegge da lì (la storia non si riscrive).

**Layout applicativo**:
- `app/routers/*` — route + query SQL inline; ogni router recupera i template via `from app.main import templates` (import tardivo per evitare cicli).
- `app/services/*` — logica di calcolo pura e testabile (ninebox_calc, goal_score, budget, cost, trends, importer, hr_report): i test unitari vivono qui, i router restano sottili. L'import da Excel (`importer`, `/people/import`) è di HR (0.44): censisce con tutti i campi della persona e il director titolare; il director non censisce più (form e tab Import rimossi, la POST `/people` resta accettata come carico iniziale).
- `app/templates/*` — Jinja2; i frammenti htmx hanno prefisso `_` (es. `_salary_sim.html`). Filtri custom: `|eur`, `|dt` (formato it-IT), globals `lookups()`, `lookup_label()`, `meta()`, `today()`.
- Pattern htmx: il server ricalcola e restituisce un frammento (`hx-post` + `hx-target`). **Trappola nota**: mai mettere pulsanti di submit dentro un frammento rigenerato da htmx — lo swap può distruggere il bottone prima che il click arrivi (già successo: il submit va statico, fuori dal target).
- `tokens.css` stila solo gli input con `type` esplicito (`input[type=text]`, …): un `<input>` senza `type` esce con lo stile del browser.
- Router per area: `org` (persone, team, riporti), `reorg` (simulazioni), `compensation` (salary, piano, budget, montepremi, assunzioni), `listino`, `ninebox`, `review` (cicli), `interactions` (note, azioni), `reports`, `settings` (configurazione del director), `company` (configurazione aziendale), `admin` (pannello del site admin); `auth` e `public` stanno in `app/`.

**Semantiche di dominio non ovvie**:
- Gli aumenti non si applicano mai direttamente: nascono come proposte (`ral_proposal`, stati bozza→proposta→approvata→applicata/respinta); solo l'applicazione genera il `ral_event` (e la `employment` nuova se cambia livello). Budget: residuo = tetto − applicato − **impegnato** (proposte pendenti). Nel piano si conferma la **nuova RAL** (è quella che decide HR, di norma diversa dall'aumento proposto): `ral_proposal.amount` resta il delta, ricalcolato dal server come nuova RAL − baseline (RAL corrente + tranche pendenti che la precedono) — è quel delta che consuma il budget.
- La Δ mostrata nella RAL timeline è **derivata** dalla timeline visibile (`cost.derive_deltas`), non il `delta` salvato: void e reinserimenti non possono sfasarla. Il `delta` in tabella resta il dato di budget. Chi calcola una RAL a una certa data usa `cost.current_ral(pid, on_date=...)`, mai la RAL "più recente in assoluto".
- Pesi degli obiettivi review: 100% **per categoria** (professionale e personale separatamente), mai sommati insieme.
- Montepremi: peso composito = casella 9-box × ruolo × rating review × obiettivi, fattori accendibili per pool (`use_*`), platea con `included` per allocazione; i `final_amount` ritoccati a mano (≠ proposed) sopravvivono a rigenerazioni e ridistribuzioni. **Premio di ruolo di HR** (0.43, `bonus_pool.kind = 'ruolo'`, `compensation._generate_ruolo`): peso = moltiplicatore aziendale del ruolo (`bonus_role_factor`, Azienda → Premi, classe `company`), sul ruolo **prevalente nell'anno di competenza** (`budget.role_prevalente`, non l'attuale: il premio di primavera guarda all'anno prima) e modificabile per allocazione (`bonus_allocation.role_type`, `role_proposed`); platea = team scelti (`teams` JSON, vuoto = tutti), in organico alla `ref_date`, ruoli esclusi (`excluded_roles`), più esclusioni a mano. Ciclo (0.46): bozza (solo HR) → «in approvazione» (`POST …/send`; i director lo vedono grazie a `perimeter.OWNED_SHARED`, ciascuno con le sole sue persone, possono cambiare il ruolo delle loro persone e approvano la propria parte in `bonus_pool_approval`; HR può richiamare in bozza) → chiuso (HR). Le allocazioni di persone altrui in un contenitore condiviso sono protette dalle guardie `_p_*_pupd/_pdel`; il ricalcolo gira su `db.sys`.
- Riporto diretto (`person_assignment.manager_person_id`) **derivato, mai scelto**: `org_tree.expected_manager` risale dal team della persona ai team padre e prende il ruolo superiore più vicino tra membri e lead del team (Specialist → TL → Manager → Director; a parità il lead, poi il nome). Responsabile può essere solo un ruolo da TL in su (`org_tree.MIN_MANAGER_ROLE`): Junior e Specialist non hanno mai riporti. Nuova assegnazione, correzione e censimento lo calcolano per la persona; modifica team (responsabile) e cambi di ruolo/team passano da `_verify_reports`, che se qualche riporto altrui non torna manda a `/org/riporti` (correzione in place o cambiamento reale con data). Le posizioni aperte usano la stessa regola, dopo il riporto del sostituito.
- Grafico linee di riporto (`org_tree.build_chart`): una riga per ruolo da TL in su più una per tutti quelli sotto. I rami che passano da team intermedi senza responsabile (es. Operation → PMO → PM Lead/PM Tech) si raccolgono in una casella di raggruppamento (`kind: "group"`: l'etichetta del team centrata nello spazio della casella del manager che manca, con sotto «coordinatore:» il responsabile della scheda team se attivo); se quella riga non è libera i rami scendono di una.
- Simulazioni di riorganizzazione (`/org/sim`, `app/services/reorg.py`, migrazione 0021): una simulazione salva **solo le differenze** dalla realtà (`reorg_team` = team nuovi con id virtuale negativo `-reorg_team.id` o override completi di team reali, `reorg_move` solo per chi cambia team/ruolo o esce (`hidden`, applicando non si tocca), `reorg_position` ipotetiche (nuove assunzioni, disegnate come posizioni in budget; o `internal` = figura di un altro team, titolo = nome, disegnata come persona che cambia team), `reorg_position_move` per le posizioni aperte del budget spostate di team/ruolo o nascoste con `hidden`, che applicando non si toccano); lo stato = realtà di oggi + differenze, con riporti sempre ricalcolati (anche l'"attuale" nei confronti, per non mischiare i riporti reali da verificare). Si modifica solo in `bozza`; `approvata` si applica con una data: team creati/aggiornati in place, spostamenti come nuove assegnazioni storicizzate, posizioni del budget aggiornate in place (team/ruolo, solo se ancora aperte), poi `_verify_reports`. Le posizioni ipotetiche non entrano nel budget assunzioni.
- Team: si **elimina** solo se vuoto e senza storia (né assegnazioni, nemmeno chiuse, né posizioni); se resta solo storia si **archivia** (`team.archived_at`): sparisce da organigramma, grafico, simulazioni e select, ma le assegnazioni passate continuano a puntarci. Le liste di team "vivi" filtrano `archived_at IS NULL`; i calcoli su storico/discendenti no. Motivi in `org._team_blockers` (`block` = vivo, `history` = solo storia).
- Modalità pubblica (`app/public.py`, switch in fondo alla barra laterale): flag **per utente** `app_user.public_mode`, letto dal middleware `auth_guard` a ogni richiesta (ContextVar) e persistente fino allo spegnimento; non oscura le pagine degli altri utenti. Le pagine riservate (`public.BLOCKED_PREFIXES` + sotto-route RAL/benefit/incentivi/allegati/sostituzione della persona) rispondono 403 a qualunque metodo, `/` rimanda a `/org`. Le cifre passano da `|eur`, che in pubblica stampa `•••`; `|eur_plain` solo per ciò che resta mostrabile (listino per codice, in chiaro; per team e dettaglio per persona non si mostrano). Valori grezzi fuori da `|eur` (input precompilati, dati JS) vanno chiusi con `{% if not public() %}`: ogni pagina condivisibile nuova va aggiunta all'audit in `tests/test_public.py`.
- Listino (`/comp/listino`, `app/services/listino.py`): costo/giorno = costo azienda annuo ÷ giorni fatturabili, calcolo puro senza DB. Il **codice di listino** (`listino_profile`) sta sulla `person_assignment` corrente: platea = chi ne ha uno, niente flag a parte. Dalla 0.41 codici e parametri sono **aziendali** (classe `company`, parametri `listino_*` in `app_meta`, gestiti da HR in Azienda → Listino): tutti i director leggono gli stessi numeri; l'anno è convenzionale, 365 giorni − 104 weekend − festività come numero medio (10) + chiusure, niente calendario dell'anno. Il director imposta il codice e formazione/interne/saturazione delle sue persone (`listino_person_param`, NULL = globale); HR consulta; filtri cumulabili codice/team/ruolo (e director per HR). Il frammento htmx non contiene controlli: il select del codice sta nella card statica.

**Test** (`tests/`): unit sui services + e2e con `TestClient`. `conftest.py` imposta `TEAMER_DB_PATH`/`TEAMER_DB_KEY_FILE` temporanei; fixture `app_db` (director `coo` e admin `it`), `client` (loggato come coo, e le query scritte nel test girano nella sua sessione, con le sue viste), `client2` (secondo director `dir2`), `hr_client` (utente `hr1`), `admin_client`, `fresh_db` (solo connessione di sistema); `tests/test_viste_hr._seed` crea un team e due persone per director; `as_user("…")` esegue query nella sessione di un utente; utenti e audit si leggono sempre con `db.sys`. Fatti del motore SQLite/SQLCipher su cui poggiano i perimetri: `tests/test_sqlite_viste.py`; scritture SQL dell'app verificate sull'AST: `tests/test_sql_scritture.py`. Le feature nuove si verificano anche con uno script e2e usa-e-getta che percorre il flusso reale via HTTP (server su una copia del DB, mai su `data/teamer.db`).
